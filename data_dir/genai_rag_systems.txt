GENAI ENGINEERING TOPIC 2: RETRIEVAL-AUGMENTED GENERATION (RAG) SYSTEM DESIGN
===========================================================================

Retrieval-augmented generation is an engineering pattern that couples a generative model with an external knowledge store, typically to improve factual grounding, reduce prompt length by referencing only relevant passages, and enable updates without retraining the base model. The system can be treated as a pipeline with distinct stages: document ingestion, chunking, embedding, indexing, retrieval, context assembly, and generation. Each stage has quality and performance knobs, and production reliability usually depends more on these knobs than on the language model alone.

Ingestion begins with acquiring documents and normalizing them into a canonical text representation. The engineering challenges include handling heterogeneous formats (HTML, PDF, Markdown), preserving structure (headings, tables), and maintaining stable identifiers for traceability and updates. Chunking then splits documents into retrieval units. Chunk size is a fundamental trade-off: small chunks improve recall for narrow queries but can reduce answer completeness because context is fragmented; large chunks improve coherence but reduce retrieval precision and increase token budget consumption. Overlap between chunks (sliding windows) can mitigate boundary effects but increases index size and may lead to redundant retrieval results. A good engineering practice is to tune chunk size based on the downstream model’s context window and the expected granularity of questions.

Embeddings map chunks and queries into a vector space where semantic similarity corresponds to geometric proximity. From a system viewpoint, the embedding model defines the retrieval “representation layer,” and its dimensionality D affects both index size and search cost. The key is consistency: the same embedding model (and preprocessing) must be used for both chunk vectors and query vectors. Many failures in RAG are mundane: inconsistent normalization, different tokenization, or a silent model version change that shifts the embedding space. Engineers typically mitigate this with explicit versioning of embedding models and re-embedding workflows when versions change.

Indexing commonly uses approximate nearest neighbor (ANN) methods to retrieve top-k vectors quickly at scale. Popular families include HNSW graphs and IVF-based inverted indexes, often with product quantization to reduce memory. HNSW provides strong recall and fast queries but can be memory-intensive; IVF+PQ can scale to very large corpora with bounded memory but may require careful tuning of the coarse quantizer and probe counts. The index must support updates (additions, deletions) and potentially multiple namespaces or tenants. In multi-tenant settings, engineers choose between separate indexes per tenant (strong isolation, higher overhead) and a shared index with filters (lower overhead, more complex query-time filtering and possible recall degradation).

Retrieval is not only vector similarity. Hybrid retrieval combines dense vectors with sparse lexical signals (BM25 or learned sparse representations). This is valuable because vector similarity can miss exact entity matches, identifiers, or rare terms, while lexical matching can miss paraphrases. A practical design is to retrieve candidates from both systems and then merge and re-rank. Re-ranking can be done with a cross-encoder (a smaller Transformer that scores query–document pairs) or with lightweight heuristics. Cross-encoders improve precision but add latency proportional to (k candidates), so engineers often deploy a two-stage approach: retrieve k=50–200, then re-rank down to k=5–20.

Once passages are selected, the context assembly stage constructs an input that the generative model can consume. This is a token-budgeting and ordering problem: passages must be de-duplicated, trimmed, and arranged to maximize utility per token. Common engineering techniques include maximal marginal relevance (MMR) to promote diversity among retrieved passages, rule-based prioritization of headings or summaries, and dynamic truncation based on passage salience. Another pragmatic trick is to keep a compact “evidence block” with short citations (document ID + chunk offsets) while placing full passages in a separate section, enabling downstream evaluation of whether outputs can be mapped back to specific sources.

Evaluation and tuning for RAG are best framed as an information retrieval problem followed by a generation problem. Retrieval metrics include recall@k (does the gold passage appear in top-k) and nDCG (rank quality). Generation metrics may include correctness or exact-match scoring for structured questions, but engineers often rely on task-specific checks (e.g., whether a generated answer references the correct identifier). A highly actionable approach is to build a labeled dataset of queries with known supporting passages, then iterate on chunking and retrieval parameters to maximize recall@k before spending effort on the generator. If retrieval fails, generation cannot recover reliably.

Operationally, RAG systems need refresh pipelines. Document updates require chunk regeneration and re-embedding, with strategies for incremental updates to avoid full re-indexing. Engineers must also handle cache layers: query embedding caching, ANN query caching for repeated queries, and passage text caching to avoid storage round-trips. Latency budgets often force a design where retrieval and re-ranking are bounded by timeouts; therefore, the system should degrade gracefully by returning fewer passages or skipping re-ranking when necessary. At scale, RAG is fundamentally a distributed systems problem: correctness depends on consistent versioning (documents, embeddings, indexes) and performance depends on managing CPU/GPU resources across embedding, ANN search, re-ranking, and generation workloads.
